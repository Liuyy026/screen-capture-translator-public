# Koma 双端开发计划（Windows 优先执行版）

更新时间：2026-09-14。首版日期：2026-09-12；所在目录保留首版日期，本文以本次更新时间为准。

本次根据 [当前进度](../当前进度_2026-09-14.md)、[七项目标](../03_结构识别与对白单元_2026-09-14/七项目标与实施方向_2026-09-14.md)、现有源码和已保存评测修订计划。首版正文保留于 [首版历史快照](双端开发计划_首版历史快照.md)。本次只更新计划和文档索引，没有运行测试、OCR、模型推理或实施下述开发任务。

## 1. 当前判断与首版范围

**Windows 已具备单页识别、翻译和覆盖验证链路，下一步先修结构准确性，再补齐编辑与批处理工作流，最后做安装发布。** macOS 保留 SwiftUI，待共享业务规则稳定后对齐；近期不以统一两端 UI 为前置条件。

首版服务于漫画或图片文件夹：打开直接包含图片的文件夹，日文 OCR、本机 Ollama 翻译为简体中文、三种阅读显示、逐句编辑保存和重译、整文件夹处理、停止及缓存复用。图片原件只读，覆盖失败可保留原图并显示原因。

暂不扩展到截图、全局快捷键、悬浮翻译、ZIP/PDF、子文件夹递归、跨页人物记忆、术语表、汉化图片导出或专业擦字排版。分组修复与人工纠正属于现有质量目标；OCR 自由补框、画框工具另行评估。

七项目标仍为 **1 项基本完成、5 项部分完成、1 项总体验收未达成**。这是质量目标状态，不能作为 Windows 功能完成百分比或发布进度。

## 3. 技术方案与共享边界

### 3.1 前端与执行模型

- Windows 继续使用 PySide6；macOS 保留 SwiftUI/AppKit。PySide6 macOS 构建作为后续选项，不要求近期重写原生界面。
- OCR 与翻译继续由 Python worker 按页在独立进程中执行，Windows 使用 `QProcess`。批处理先采用串行页面队列，避免 OCR、翻译和多模型同时占用显存。
- 保留本地 Ollama `127.0.0.1:11439`、关闭云端、仅使用已下载模型的约束。当前默认继续使用 `qwen3:4b-q6k` 和 `blocks`；结构修复期间保持模型与提示词稳定。

### 3.2 当前 worker 协议

以下为已有参数，界面接入时继续兼容：

```text
--image <图片路径>
--operation ocr|translate|both
--model <已安装的 Ollama 模型名>
--status <状态 JSON 路径>
--block-id <可选，单块重译>
--batch-size <批次大小，默认 8>
--translation-unit blocks|dialogues
```

`--status` 为必填。没有图片缓存时，`translate` 也会先执行 OCR，界面应据此提示处理阶段，不能把它解释成一定跳过识别。

stdout 保持单个 JSON：成功为 `{"ok":true,"cache":"..."}`，失败为 `{"ok":false,"error":"...","cache":"..."}`。状态文件提供 `message`，OCR 日志走 stderr。页面内个别译文失败仍可能得到进程级 `ok:true`，界面必须继续读取缓存中的错误和待处理项，区分“流程结束”与“全部译文可用”。

计划补充请求标识和任务独立状态文件，避免停止、快速切页和启动下一任务时旧结果污染当前页。若增加编辑操作或协议字段，保持已有 OCR/翻译调用兼容，并同步补充契约测试。

### 3.3 共享数据与待收敛业务

| 内容 | 当前做法 | 后续处理 |
| --- | --- | --- |
| 页面缓存 | 图片内容 SHA-256；Windows 使用 `%LOCALAPPDATA%\KomaReader\pages`，macOS 使用 `~/Library/Application Support/KomaReader/pages` | 前端复用共享路径规则或 worker 返回值，减少重复计算 |
| 读写编码 | worker 缓存、状态及相关日志已显式 UTF-8，Windows 启动保留 `-X utf8` | 审核进程 stdout/stderr 及其余文件读写，不再将全部 UTF-8 适配标为未开始 |
| 编辑保存 | worker 保留人工译文；SwiftUI 直接序列化缓存 | 抽出共享编辑操作，由后端保留未知字段、结构字段和人工标记，避免旧前端保存丢字段 |
| 缓存失效 | 已有结构迁移、模型/翻译模式变化处理和原子写入 | 明确原文编辑、手动分组、单句重译的失效范围；禁止 worker 与编辑器并发覆盖同页 |
| 模型与日志 | 开发模式使用项目 `.models` 和 `.runtime` | 安装版区分只读程序目录与可写用户数据；预留旧数据迁移 |
| Ollama | 启动器检测端口后尝试启动服务 | 增加 API 就绪与模型可用性检查；记录服务归属，退出时只管理本应用启动的服务 |

## 4. Windows 开发顺序与验收关口

按依赖推进，不按尚未验证的工期承诺排日期。每一阶段提交变更说明、对应验证结果和剩余失败清单；阶段通过后再扩大范围。

### W1：修复结构识别与建立可信标注（P0，下一项）

对应目标 1、2、3、6。主要位置：`backend/panels.py`、`backend/structure.py`、结构夹具与标注评分脚本。

1. 固定现有 OCR、图片摘要、模型和 v5 预测基线，先处理第 16 页分镜漏检与跨分镜错序。
2. 修复第 16 页成员 1/2、6/8 和第 24 页成员 1/2 的连通气泡拆散，保留原始块编号、来源与可解释诊断。
3. 同时检查“应合并”和“相邻但不得合并”的案例；分镜候选只用于结构约束，不能直接授权擦除。
4. 补齐第 40、58 页独立标签，再从固定集扩充横排、竖排、多叶气泡、无框文字和复杂分镜样本。建议先形成至少 15 页分层复核集，并保留未参与规则调试的页面；此数量是计划建议，不是已有成果。

**通过条件：**第 16 页与独立标签一致地恢复 3 个分镜、7 个对白，第 24 页恢复 5 个对白；同时匹配成员集合、全页顺序与组内顺序，不能仅比较数量。第 8 页与既有回归无新增错误。报告标签来源、有效页数、未标注页数及全部失败案例，助手抽查和人工确认分别统计。

**阶段汇报点：**先交付目标 2、3 的结构修复结果。此阶段复用 OCR，无需因改动分组规则就立即重跑全部模型对比。

### W2：补齐 Windows 编辑与任务工作流（P1）

依赖 W1 的结构字段和失效规则稳定。主要位置：`windows_app.py`、共享缓存/编辑模块、worker。

| 工作包 | 交付内容 | 验收 |
| --- | --- | --- |
| 对白定位与编辑 | 画布选框与侧栏联动；原文/译文编辑、保存、未保存状态；按既有分组键接入合并/拆分纠正 | 保存重启后仍在；改原文使相关旧译文和整句映射失效；普通批量翻译不覆盖人工译文 |
| 单句重译与模式 | 接入 `--block-id`；提供逐块/完整对白选项及当前模式；重译人工句子时明确替换意图 | 仅目标句被重译；相关对白缓存正确失效，其他人工修改保留；默认仍为逐块 |
| 文件夹队列 | 单页串行处理、总数/已完成/失败/当前页、停止、失败项重试 | 停止后不再启动下一页；已完成缓存可读，失败页可追溯，恢复不覆盖已保存人工译文 |
| 阅读状态 | 图片缩略列表；记住文件夹、当前页、模型与显示模式 | 重启恢复；目录被移动或图片被删除时给出有效提示，允许重新选择 |
| 进程健壮性 | 独立任务状态、进程启动错误、stderr 提示、关闭窗口取消与结果归属校验 | 快速切页、连续启动/停止、空目录、损坏图片、worker 崩溃不串页、不显示陈旧完成状态 |

共享编辑规则先在 Python 实现，再接入 Windows；macOS 对同一规则的接入安排在 M1。批处理优先保证状态正确与可恢复，性能优化后置。

### W3：验证翻译质量与覆盖排版（P1）

对应目标 4、5、6、7。依赖结构稳定和可用的检查/纠正工作流。

1. 固定同一批页面、同一 OCR 和结构版本、同一模型摘要与推理参数，比较逐块和完整对白。结构、协议或模型改变时才安排必要的新 A/B；所有新实验使用独立输出目录。
2. 在有独立原文核查和参考译文的样本上，评价代词、称呼、断句、语气、否定/比较关系，以及整句拆回成员块的对应。检查第 8 页已发现的语义问题。
3. 可信且成员完整匹配时整句排版；`whole_only` 不按字数硬拆。整句布局不成立时只使用确实可用的逐块译文，否则保留原图并记录原因。
4. 分别复核气泡区域是否正确、是否伤及人物/背景、中文是否溢出或不可读，以及冷启动、缓存命中和翻译耗时。

**通过条件：**自动指标与人工质量分开报告；每项给出样本范围、有效分母和失败例。冻结复核集上不能有未处理的严重画面误伤；无法安全覆盖的区域必须回退。只有完整对白在语义、对应和显示质量上有可复查优势，且额外耗时可接受，才考虑更改默认模式。

结构正确率、人工语义评分及可接受耗时阈值在扩充标签并取得基线后固定，再执行验收；目前没有依据填写“95% 准确率”等承诺。阈值未固定或对应分母不足时，阶段保持待验收。

### W4：Windows 可迁移发布（P2）

在 W1～W3 达标后收尾发布；不把本机双击启动成功视为安装包验收。

- 安装/检查流程覆盖运行时、PySide6、OCR 依赖、模型存在性、磁盘空间、服务探活和日志入口；CPU 与 CUDA 路径分别验证。
- 解决 `.runtime/python` 与 `pyvenv.cfg` 的绝对路径耦合；源码开发使用独立环境，安装包不能复制开发机虚拟环境后直接宣称可迁移。
- 网络诊断区分 DNS/hosts、代理、TLS 和下载失败；支持进程级代理配置，保持证书校验。早期 hosts 冲突仅作为历史故障案例，不能推断当前网络状态，也不写死公网 IP。
- 在新用户或干净 Windows 环境中验证中文/空格路径、普通权限、项目移动、重启、缺模型、服务端口冲突和断网提示。
- 验证 100%/150%/200% DPI、较小分辨率和 WebP/PNG/JPG 等已声明格式；图片与文字不得出现不可操作的遮挡。
- 原图不可写；升级保留缓存和人工译文；卸载默认保留用户数据。安装包版本、依赖和模型清单可追溯。

**发布关口：**实际发布候选版本的回归测试、样图链路、固定集质量复核和 Windows 使用流程均有记录；无未处理的缓存破坏、原图改写、串页和人工译文丢失问题。支持的 Windows 版本与最低资源配置以安装验证结果发布，RTX 5070/约 12 GB 显存、32 GB 内存只是当前验证硬件。

### M1：macOS 对齐与双端发布（P2，Windows 稳定后）

- 保留 SwiftUI 体验，将直接编辑缓存改为调用共享业务操作，兼容新版结构、译文映射和诊断字段。
- 在 macOS 独立创建环境，验证同一后端契约、人工修改保留、单句重译、批处理取消、缓存迁移和模型切换。
- 两端分别检查进程、用户数据路径和安装升级；在实际 macOS 机器运行后再宣称双端验收完成。
- 后续是否统一 PySide6 UI，依据维护成本和使用体验另作决定，不重新引入首版尚不需要的前端工具链。

## 5. 评测基线与统计规则

### 5.1 已保存的固定 62 页结果

来源：v5 A/B 汇总（本地文件：`.runtime/benchmarks/units-v5-fixed62/summary.json`）。本次只读取已有结果，未重新推理。

| 指标 | 逐块模式 | 完整对白模式 |
| --- | ---: | ---: |
| 模型 | qwen3:4b-q6k | qwen3:4b-q6k |
| 页面 / 可翻译块 / 对白单元 | 62 / 627 / 604 | 62 / 627 / 604 |
| 自动完整单元 | 543/604（89.9%） | 589/604（97.5%） |
| 有成员译文的块 | 565/627 | 593/627 |
| 只有整句、无逐块映射的单元 | 0 | 9 |
| 总页面处理耗时 | 95.3 秒 | 205.3 秒 |

完整对白模式自动完整率较高，记录耗时约为逐块的 2.15 倍；两者都不是人工语义准确率。该批复用 OCR，耗时不能解释为首次打开图片到完成 OCR 的全流程性能。旧量化评测的 98.41% 使用另一协议与统计口径，不与这里的 97.5% 直接比较。

结构评分（本地文件：`.runtime/benchmarks/units-v5-fixed62/annotation-score.json`）目前有 5 页模板、3 页助手抽查、2 页未填写、0 页人工确认；对白精确匹配指标仅覆盖第 16、24 页。最近一次完整测试记录为 93 项通过，来自已有进度记录，本次没有重新验证。

### 5.2 后续报告必须保留的分母

| 评估层 | 必须记录 | 不能替代的判断 |
| --- | --- | --- |
| OCR | 经原图核查的检测框、文字、方向及漏检情况 | OCR 指纹一致只证明输入一致 |
| 分镜与分组 | 独立标签页数、成员集合精确匹配、合并/拆分错误 | Jaccard 覆盖率不等于严格正确率 |
| 阅读顺序 | 有顺序标签的页面及对白内部成员，分别检查 | 编号连续不等于顺序正确 |
| 翻译 | 自动完整数/有效单元数；人工复核句数与各类语义错误 | 非空、可解析、无协议错误不等于译对 |
| 覆盖 | 人工复核区域数、严重/轻微误伤；轮廓外像素独立统计 | 0 轮廓外像素不等于 0 实际误伤 |
| 排版与性能 | 已排版/满足前置条件区域；待处理与失败数；冷/热耗时 | 未翻译不算排版失败；缓存耗时不代表冷启动 |

## 6. 下一次开发的具体起点

1. 读取第 16、24 页现有结构夹具、原图和实际缓存，固定失败基线与标签来源。
2. 只推进 W1 中的分镜、连通气泡和阅读顺序修复，对同一 OCR 做结构回归。
3. 汇报目标 2、3 的前后差异、受影响页面与仍失败的案例，再进入 Windows 编辑和任务工作流。
4. 每次完成后同步当前进度中的状态、证据路径和测试日期；实现、测试通过、产品验收及发布分别记录。

本计划中的任务均为后续安排；本次修订不改变已有代码、实验产物或模型配置。
